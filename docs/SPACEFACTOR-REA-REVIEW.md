# SpaceFactor: evidence and independent improvements

Reviewed 2026-10-15. References: [SpaceFactor](https://www.spacefactor.cn/),
[Layout Studio public demo](https://layout-studio.spacefactor.cn/),
[REA skill](https://github.com/morluto/rea/blob/main/.agents/skills/reverse-engineer-anything/SKILL.md).

The public demo is stronger than our previous workflow at making an arrangement
immediately visible in a navigable 3D space. This is an observed workflow gap,
not evidence that its solver, construction accuracy or complete product is better.

## Method and evidence boundary

Used REA 6.5.0 through its CLI with a dedicated temporary Chromium profile,
alongside independent in-app browser inspection. No account, personal drawing,
supplier data or private API was used. No agent registration was changed.

Declared REA scenario: open the demo; choose its public sample; wait for the
workspace; select the child's room's second furniture scheme; capture DOM,
accessibility, screenshot and network metadata. Request/response bodies, storage
and header values were not requested. The machine-readable ledger is
[evidence/spacefactor-rea-2026-10-15.json](evidence/spacefactor-rea-2026-10-15.json).

The first run returned Evidence
`ev_caaa22a35c2cd8cbc45c91916549944b637f0db0bedf01a5d3ff2dd44933ff15`
with incomplete scene-readiness coverage. The second run completed every declared
action and captured the final selected scheme and model, but REA reported failed
cleanup verification and returned a partial observation inside an error envelope.
That limitation is preserved; it is not a fully successful REA run. A subsequent
check found no Chrome process carrying REA's temporary scenario-profile prefix.
The in-app browser independently opened the sample and changed the same scheme.
Readiness timing on this loaded host is not used as a product-speed benchmark.

## Findings

| Question | Evidence | Conclusion and boundary |
| --- | --- | --- |
| Can someone understand a real space without uploading or logging in? | Public sample opened to five rooms and a 69.0 m² summary. | Observed no-login sample path. Our local sample already exists. |
| Do choices visibly change the room? | Per-room selectors expose several schemes; selecting the second child's-room scheme produces a confirmation and changed 3D furniture. | Observed arrangement switching. The scheme-generation method and training data remain unknown. |
| How is the spatial representation controlled? | Public workspace exposes orbit/top/room views, parallel projection, wall cuts, day/night and PNG export. | Direct controls reduce the distance between an option and its visual consequence. |
| Is each switch generated by a model service? | REA retained 36 network events, none in the selected-switch/one-second-settle interval. | Consistent with locally selecting loaded data for this sample. It does not establish offline support or behavior of uploaded plans. |
| Does the demo expose geographic sun controls? | Inspected lighting panel presents day and warm night choices. | No city/date input was observed in that inspected panel. Other products or authenticated features are unknown. |
| Are its furnishing catalog, assets or solver reusable? | No permissive source/asset license was established. | No reuse. Our implementation uses existing schematic meshes, dimensions and local search. |

Its rich furniture geometry/materials also make the sample more recognizable.
Our user's requested low-detail architectural representation remains appropriate:
clear walls, openings, furniture footprints and real sun/shadows. A photograph
does not substitute for editable geometry or establish construction fidelity.

## What changed in designon

1. A/B contains actual measured drawings, with one metre at the same screen
   scale and a common north-west origin. Stable room numbers and accent outlines
   identify matching rooms and changed furniture.
2. One local 3D canvas switches A/B while holding camera, crop, cut and sunlight.
   It reuses the main renderer's physical wall/opening/furniture components and
   cached shadows. Export is the full PNG frame, never an option-specific crop.
3. Room options can be inspected in the full house before Apply. Opening or
   orbiting a preview does not alter the saved plan. Existing measured previews,
   conservative door checks and explicit Apply/Undo remain.
4. Plan A is saved as one nonrecursive snapshot with the project. Reload, share
   and JSON preserve it. Restore A is one undo step, retaining both alternatives.
5. Room-level distances and fit issues explain furniture changes that leave
   shell cost/heat/carbon metrics unchanged. No synthetic comfort score, lux or
   accessible-route claim is added.

These are independently implemented advantages on the measured comparison task.
They do not establish superiority over SpaceFactor's layout quality, product
catalog, upload recognition or paid services; those need separate evaluation.
Existing city/date SunCalc studies and local/offline operation are retained.

## Validation

Build, lint, 418 frontend tests and 54 Worker tests pass. The full 110-case
Chromium desktop/phone suite passed; the six comparison cases were rerun after
adding explicit contrast/type/44px checks and correcting an inherited 11px footer
button style. Every palette passed. Browser assertions verify genuine storage
reload/share, Restore/Undo, distinct offline A/B frames, byte-identical return to
an orbited camera, full-frame PNG bytes and inert room-options previews. Existing
idle GPU, shadow-cache, city, model-export and A4-study-sheet checks remain green.
Screenshots were inspected at 375, 768 and 1280 px.

A fresh adversarial review caught a physical-coordinate defect in the first
shared-site implementation: rescaling percentages changed existing opening
association tolerances. Rendering now resolves original topology before applying
common drawing/camera transforms. The unequal-site unit regression and an
independent asymmetric-site room/rotated-furniture check pass; no confirmed issue
remained in that recheck. The lesson was captured and recalled in SecondBrain.

Production dependency and Worker audits report zero vulnerabilities; Worker
quota/concurrency proof passes. Seven existing development-only advisories remain.
No source/bundle match was found for provider-client hosts, key literals, builder
branding or localhost URLs. The previously unavailable Axiom CLI (registry 404)
is not reported as a passed design gate. No new runtime dependency was added.
