# designon — System Audit

**Date:** 2026-10-20 · **Tree:** `29ffdc9` + the landing-sheet work in this commit
**Scope:** maintenance, shipability, design, and the mathematics the system is built from.

## How to read this

Every claim carries a `file:line` citation. Three labels are used and they mean
different things:

- **Verified** — I read the source or ran it myself in this session.
- **Reported** — extracted by a read-only exploration pass and spot-checked by
  me at the cited line. The formula is quoted from source, not inferred.
- **Not covered** — named in the appendix so nobody reads silence as a clean bill.

Two claims from the exploration pass were **refuted** by checking them
(§4.6 print sizing, §4.3 polar azimuth). They are listed here because a wrong
audit is worse than no audit.

Gates at this tree: lint clean, `tsc -b` clean, **543 unit tests across 67
files**, **54 worker tests**, **172 browser tests across desktop and mobile**
(6.1 min). `npm audit --production` → 0 vulnerabilities.

## 1. Design

### 1.1 The documented accent is not the shipped accent — **Verified**

`AGENTS.md` says *"One accent: amber `#f59e0b`"*. The running system does not
use amber.

- `src/styles.css:57` declares `--accent-primary: #f59e0b`.
- `src/design/studio.css:26` declares `--accent-primary: var(--studio-sienna)`.
- `src/main.tsx:8-9` imports `styles.css` **then** `design/studio.css`, so the
  later sheet wins. The measured value in the browser is `#8a4c16`.

The studio is not single-hue amber; it is the **Wada 243** palette
(`src/design/themes.ts:8-13`) with four named appearances — Solar Pop, Guava
Club, Violet Hour, Drafting Room — each carrying its own paper, ink, rail and
**action** colour. The default theme's action colour is `#8a4c16`, deepened
from Raw Sienna in Sanzo Wada combination 243 (`docs/PALETTE.md`).

This is a documentation defect, not a design defect: the system is coherent,
the rule of one accent holds per theme, and `AGENTS.md` simply describes an
older generation. But the rule that everything else obeys is written down
wrong, which is how a second accent eventually gets added.

### 1.2 Tailwind is a reset wearing a utility framework's clothes — **Verified**

`tailwindcss@^3.4.17` is a devDependency and `src/styles.css:1-3` carries the
three `@tailwind` directives. But:

- **Zero Tailwind utility classes are used.** All 11 apparent matches for
  `grid`/`flex` in the markup are custom class names (`study-sheet-grid`,
  `variant-grid`, `scenario-grid` …).
- `tailwind.config.js` still names **Inter** and **Manrope** as the font
  families and `citron` as a colour. The product uses Source Sans 3 and
  JetBrains Mono and has no citron.
- What actually ships is the **preflight layer** — the built CSS contains
  `h1,h2,h3,h4,h5,h6{font-size:inherit;font-weight:inherit}`, a Tailwind
  reset rule.

So the dependency earns one CSS reset and carries seven dev-only advisories
with it. AGENTS.md calls it a *"Tailwind foundation"*; the honest description
is *"a Tailwind preflight plus 8,500 lines of hand-written CSS"*.

### 1.3 The type scale is documented, not enforced — **Verified**

The studio declares `--font-title: 22px`, `--font-body: 16px`,
`--font-note: 12px` (`src/design/studio.css:41-43`). The browser suite
enforces exactly that set inside the comparison dialog
(`e2e/comparison.spec.ts:214`), but outside it the app has drifted to 11px
(`src/styles.css:2303`), 13px, 18px (`src/styles.css:2340`) and 20px.

### 1.4 The landing sheet — **Verified**

`src/components/assembly-guide.css` is scoped entirely under
`.assembly-guide.welcome-gate`. The palette is not global: `--bau-red` is
declared on the sheet, and the test asserts it is **absent from
`:root`**. The studio's own accent is untouched and asserted separately.

Colour does one job each, and the job is functional rather than decorative:

| Colour | Means | Appears as |
|---|---|---|
| red `#d62b1f` | your mark — the drawing you make | the pencil, step 01, the primary call to action |
| blue `#17458f` | the measure — the dimension you give | the plan, the floor plinth, step 02 |
| yellow `#f6c31b` | the light — the sun you read | the sun, the daylight patch, step 04 |
| ink `#16161a` | structure, type, rules | outlines, the four-step band |
| paper `#f0ece1` | the ground | the sheet |

The title block under the drawing prints the sample's **own computed figures**
(`src/components/WelcomeGate.tsx:9-30`): envelope 8.75 × 5.71 m, net area
50.0 m², 6 spaces / 4 doors / 6 windows. They are derived from
`chinaApartmentPlan` by `totalAreaFor`, not typed in, so they cannot drift
from the model. The caption says **"Not to scale — dimensions taken from the
plan"**, because the axonometric genuinely has no scale bar.

## 2. Maintenance

### 2.1 The gate that catches real defects is outside the gate set — **Verified**

`npm run verify` = `lint && build && test && verify:worker`. It **does not run
the browser suite** (`package.json:7-16`). The browser suite is the only gate
that caught the print-scale defect (the same plan measured 231.7 mm wide with
short room names and 220.0 mm with long ones, while `tsc`, ESLint and all 543
unit tests stayed green), and it is also the only gate that can see the
landing sheet at all.

**Consequence:** the standard "did I break anything" command cannot detect a
large class of regressions. This is the single highest-value maintenance
change available.

### 2.2 Two file-size cliffs — **Verified**

`src/App.tsx` is 1,863 lines and `src/components/Inspector.tsx` is 1,208.
Every other source file is under 920. These two hold most of the workspace's
state orchestration and most of its analysis copy, and they are the reason
the layering gate (`src/layering.test.ts`) had to be written.

### 2.3 Three tolerances for "this opening is on that wall" — **Reported, spot-checked**

- `src/analysis/walls.ts:5` — `EPS = 0.5` percent for "touching / shared wall"
- `src/analysis/walls.ts:70-73` — `1.5` percent for "on this edge"
- `src/canvas/geometry.ts:117` — `WALL_SNAP_PCT = 5`

Three numbers, three meanings, one predicate family. Nothing enforces that
they agree.

### 2.4 Two wall heights — **Reported, spot-checked**

`src/canvas/isometric.ts:7` declares `WALL_HEIGHT_M = 2.8`;
`src/plan.ts:391` declares `DEFAULT_WALL_HEIGHT = 2.7`. Every drawn wall
uses 2.7 m; the 2.8 survives in exactly one place — the opening-marker
height at `isometric.ts:108` (2.8 × 0.45 = 1.26 m).

### 2.5 Two section systems that disagree on which way you are looking — **Reported, spot-checked**

- `src/drawing/sheet.ts:459` — the drawing sheet's section *looks north*
- `src/study/StudySheet.tsx:114` — the study sheet's A–A *looks south*

Both are correct for their own geometry, and a user comparing the two sheets
sees two contradictory arrows.

### 2.6 A division guarded by the wrong condition — **Verified**

`src/study/graphics.ts:58-64` projects shadow corners with
`y * sun.vector.x / sun.vector.y`. The only guard is `sun.altitude <= 0`
(`:59`). At an altitude of 0.01°, `sun.vector.y ≈ 1.7 × 10⁻⁴`, so the hull
coordinates explode by four orders of magnitude. The guard should be on
`|sun.vector.y|`, not on altitude.

### 2.7 Dead CSS — **Verified**

Fourteen `.welcome-card` rules survive in `src/styles.css` (lines 582, 591,
4016, 4044, 4119, 4127, 4131, 4547) and `src/design/studio.css` (139, 140,
202, 203, 279, 290) after the entry sheet replaced the old welcome card. No
JSX renders the class any more.

### 3.3 Print sizing — **Verified, and the exploration pass was wrong**

The exploration pass reported that *"the sheet's physical print size is
whatever the browser's print dialog gives — nothing in the code pins it to
A4."* That is **false** in the current tree:

- `src/styles.css:7250` — `@page { size: A4 landscape; margin: 8mm; }`
- `src/styles.css:7256` — `.drawing-sheet { width: 281mm; height: auto; }`

297 mm of landscape A4 minus two 8 mm margins is exactly 281 mm. The sheet's
scale is pinned by its width alone, which is the invariant the 2026-10-18
print fix established.

The *real* distinction is different and still worth stating: **the drawing
sheet has no scale ratio**, because each panel is fitted independently
(`src/canvas/DrawingSheet.tsx:46-66`) and the scale bar's length in metres
changes with building size (1 m under 12 m, otherwise 5 m —
`src/drawing/sheet.ts:485`). The axonometric carries no scale bar at all. Only
the A4 study sheet carries a stated ratio, `1:n` (`src/study/StudySheet.tsx:135`).

## 4. The mathematics

### 4.1 The unit chain — **Reported, spot-checked**

The canonical space is **plan percentage (0–100)**, origin at the north-west
corner, +x east, +y south.

```
mx = (xPct / 100) · site.w          my = (yPct / 100) · site.h
area = (room.w/100)·site.w · (room.h/100)·site.h        m²
```

The field is **not square unless `site.w === site.h`**, so a percentage is a
per-axis scale, never a scalar.

**Calibration** — one known dimension sets the whole field
(`src/plan.ts:44-64`):

```
share          = room.w / 100
requestedScale = (knownMeters / share) / currentAxis
scale          = clamp(requestedScale, max(1/w, 1/h), min(200/w, 200/h))
```

Room proportions survive calibration; only the field's scale changes. The
field is bounded to ≤ 200 m and ≥ 1 m per axis.

**Pixels.** There is no pixel constant in the code — the mapping is CSS. The
canvas is sized `width: min(90cqw, calc((100cqh − 78px) · var(--site-ratio)))`
(`src/styles.css:7024`) where `--site-ratio` is `site.w / site.h`
(`src/canvas/FloorPlan.tsx:138`), and rooms are positioned by percentage
(`src/canvas/FloorPlan.tsx:204`). A room at 46 % of the field is 46 % of the
calibrated width in metres **and** in pixels; the canvas stores no pixel
coordinate.

**Millimetres.** The A4 study sheet sets `k = 1000/scale` mm per metre and
emits `<svg viewBox="−16 −14 paperWidth …" width="{paperWidth}mm">`
(`src/study/StudySheet.tsx:32-37`), so **one SVG user unit is one millimetre
on paper**.

### 4.2 The isometric projection — **Reported, spot-checked**

`src/canvas/isometric.ts:38-43`:

```js
x: (mx − my) · cos30 · scale
y: (mx + my) · sin30 · scale − mz · scale
```

Each unit axis projects to length exactly `scale`, and the x and y axes meet
at 120°. It is a true parallel (affine) projection and a true isometric —
no perspective, no differential foreshortening.

What is *not* true about it:

- It is **not** the 3D scene's projection. The scene uses an
  `OrthographicCamera` at 35.264° elevation / 45° azimuth
  (`src/study/geometry.ts:64-80`).
- The 2D projection **ignores wall thickness** — faces sit on the room
  boundary lines.
- Painter's ordering uses a proxy, `depth = mx + my + w + d`
  (`isometric.ts:81,89`), not the true view-space depth.
- The 2D axonometric has **no roof** — the top face sits at ceiling height.

### 4.3 Two solar models — **Verified. This is the headline.**

The codebase ships **two different solar models**, and they are used in
different layers:

| | Model | Time base | Used by |
|---|---|---|---|
| **A** | `solarPosition` (`src/plan.ts:360-379`) | **local solar time** — no longitude, no timezone, no DST | `analysis/sunHours.ts:32`, `analysis/overheating.ts:94`, `scenarios/climateScenarios.ts:74`, and `canvas/SunChart.tsx` **as its no-location fallback** |
| **B** | `citySunPosition` (`src/location/solar.ts:36-38`, SunCalc) | **civil time in an IANA zone** — longitude, timezone and DST all applied | `App.tsx:251` (the live 3D scene), `study/graphics.ts:32` (study-sheet shadows), `canvas/SunChart.tsx` when a city is set |

Model A is a closed-form approximation: declination from a fixed 23.45°
obliquity and a 365-day year, hour angle `15°·(hour − 12)`, altitude clamped to
≥ 0 so night is indistinguishable from the horizon.

**The two disagree, and the gap is not academic.** I ran both models for the
same civil hour on 21 June 2026 (`src/location/solar.ts` is a faithful copy of
the shipped code):

| City | Hour | Model A (analysis) | Model B (scene) | Δ altitude | Δ azimuth |
|---|---|---|---|---|---|
| Bangkok | 13:00 | alt 72.8, az 306.5 | alt 76.4, az 317.0 | +3.6° | **+10.4°** |
| Shanghai | 13:00 | alt 74.6, az 243.3 | alt 73.8, az 245.2 | −0.8° | +1.8° |
| Berlin (CEST) | 13:00 | alt 58.8, az 207.2 | alt 60.9, az 176.1 | +2.1° | **−31.1°** |
| New York (EDT) | 13:00 | alt 68.6, az 220.7 | alt 72.7, az 181.6 | +4.1° | **−39.1°** |
| Reykjavik | 13:00 | alt 48.1, az 200.8 | alt 49.0, az 169.6 | +0.9° | **−31.2°** |

For the two cities the product ships with, the models agree within ~10°. For
anywhere with a **daylight-saving zone** or a large offset between its zone
meridian and its longitude, they disagree by **up to 39° of azimuth**. At 13:00
in New York the analysis believes the sun is in the south-west while the 3D
scene draws it due south.

Thirty-nine degrees is enough to flip a wall's exposure: the sun-hours panel
can say a west wall is sunlit while the Spatial view shows it in shade. The
product's promise is that *every number on screen is meant to be argued with*
— but a user who argues with the **Living** panel by looking at the **Spatial**
view will find the two disagreeing, and neither carries a note saying so.

**Two corrections to the exploration pass, both checked by running it:**
- It reported a NaN azimuth at the poles. The value is finite: at latitude 90
  the denominator is ~6 × 10⁻¹⁷, the ratio is enormous, and
  `Math.max(-1, Math.min(1, cosAzimuth))` clamps it to ±1. The azimuth
  degenerates to a meaningless 188.8°, but it is not NaN.
- The DST handling in Model B is sound and worth keeping: a **repeated** hour
  takes its *first* occurrence (`src/location/solar.ts:25-26`); a **skipped**
  hour advances across the gap and the workspace reports it to the user
  (`src/App.tsx:168-174`).

### 4.4 Label placement — **Reported**

`src/drawing/labels.ts` decides every room name, **in viewBox pixels**. The
module header records why: an earlier version compared projected model units
against SVG font pixels, so it could never exclude anything and the collisions
shipped.

- **Ink box** (`:146-179`) — `INK_ASCENT 0.7`, `INK_DESCENT 0.2`,
  `INK_SIDE_BEARING 0.03`, `INSET 0.05`. The rectangle actually inked by a
  line of type, anchored exactly as the SVG renders it.
- **Width estimate** (`:83-97`) — advance width in em, explicitly *"an estimate
  for fit decisions only… never a measurement"*.
- **Band intersection** (`:202-253`) — a cut at every vertex height inside the
  band, intersected. This is what makes a name on an axonometric roof fail
  correctly: the parallelogram's diagonal extent is far wider than the strip
  the type occupies.
- **Separating-axis overlap** (`:182-194`) — touching counts as *not*
  overlapping.
- **Order** (`:267-333`) — step the type down one point at a time; on each
  attempt, measure the inked strip, find the usable band, slide the line
  inside it, then check occluders.

### 4.5 Two sheet systems, two scale regimes — **Reported**

| | Drawing sheet | A4 study sheet |
|---|---|---|
| viewBox units | unitless px (1040 × `DRAWING_HEIGHT`) | **millimetres** |
| physical size | 281 mm wide (pinned by `@page`) | `1000/scale` mm per metre |
| stated ratio | **none** | `1:n`, captioned |
| panel scaling | **each panel fitted independently** | one ratio for the sheet |
| scale bar | 1 m or 5 m, chosen by building size | the ratio |

The drawing sheet's panels are fitted one by one (`DrawingSheet.tsx:46-66`),
so the plan, section, elevation and axonometric each carry a *different*
scale on the same sheet. The sheet's own note says so — *"Concept drawing ·
panels fitted independently; use scale bar for plan"* (`src/canvas/DrawingSheet.tsx:558`). The axonometric has no
scale bar, and the 2026-10-18 fix guarantees the *sheet* holds one physical
size whatever the room names say — it does not and cannot make the four
panels agree with each other.

### 4.6 Section and elevation derivation — **Reported**

- **Section plane** (`src/drawing/sheet.ts:228-248`): for every room and both
  axes, the candidate cut is the room's mid-line; the score is the summed
  area of rooms the cut crosses (strictly inside by more than 0.02 m); ties go
  to east–west.
- **Elevation face** (`:307-329`): exterior wall spans are totalled per
  compass; the longest wins, ties break by opening count, and the iteration
  order `S,N,E,W` means **South wins an exact length tie**.
- **Walls are modelled as bands centred on the boundary line** — dimensions
  are to wall centrelines, and the study sheet footer says exactly that
  (`src/study/StudySheet.tsx:142`).

### 4.7 The analysis layer — **Reported**

Stated plainly by its own sources:

- **Daylight** (`src/analysis/daylight.ts:18,40-42`) — *"not an illuminance
  contour"*, *"answers 'where might daylight reach?', not 'how many lux?'"*.
  Reach `= min(head, roomHeight) · 1.5 · (vlt / 0.70)`, sampled on a 12 × 12
  grid.
- **Heat flow** (`src/analysis/heatFlow.ts:40-47`) — `Q = U·A·ΔT`, solar
  `800 W/m² · area · SHGC · incidence`. The source excludes **no roof, no
  floor, no infiltration, no thermal bridges, no clouds, no shading, no
  internal loads**.
- **Thermal** (`src/analysis/thermal.ts`) — `ΔT = totalHeat / netMass`, with
  `netMass = (80 + area·1.5) + (40 + ventScore·220)` Wh/°C. The solar terms
  are crude constants: a hard-coded 3.0 m wall height, 0.35 SHGC, a flat
  6 sun-hours.
- **Envelope** (`src/assemblies/envelope.ts:53-55`) — `wallRValue = 1/(U ·
  0.176)`, the imperial-to-SI factor.
- **Sun-hours** (`src/analysis/sunHours.ts`) — 06:00–18:00 in 15-minute
  steps, using **Model A**, so the hours are local solar time and cannot be
  reconciled with the SunCalc-driven scene.

## 6. Recommended order of work

1. **Put the browser suite inside `npm run verify`** (finding 2). One line in
   `package.json`; it converts the whole suite from "run it sometimes" into
   "it is the gate". Nothing else on this list matters as much.
2. **Unify the solar model** (finding 1). Route `sunHours`, `overheating` and
   `climateScenarios` through `citySunPosition` when a location exists, and
   label the fallback as *approximate — local solar time* when it does not.
   The model already exists and is already correct; it is simply not used by
   the analysis layer.
3. **Correct `AGENTS.md`** (finding 3) to describe the Wada 243 theme system
   and its one action colour, and say which surface the Bauhaus palette is
   scoped to.
4. **Guard the shadow projection** (finding 4) on `|sun.vector.y|`, not
   altitude.
5. **Decide on Tailwind** (finding 5) — either keep it and rewrite its config
   to match reality, or drop it and hand-write the ~40 lines of reset that
   the preflight currently provides.
6. **Converge the three wall tolerances** (finding 6) on one constant with
   three named uses.
